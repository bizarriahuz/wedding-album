# Load and failure test: guest uploads, 2026-11-24

For the 12 December event (harris-aqilah-a697). **Production was not touched.** Nothing ran against the production Worker (`madeofmemories`), the `wedding-album` D1 database or the `wedding-album-media` bucket.

## Summary

- **Max safe concurrent uploaders: 200.** This is the highest level tested. It gave zero 4xx/5xx errors and zero Cloudflare platform errors. Nothing broke on the Cloudflare side, so the real ceiling is higher and wasn't found. The planning figure is 80 guests plus a photobooth: 2.5× headroom.
- At 80 guests the first thing to run out will be **venue Wi-Fi uplink**, not Cloudflare. See [Expected load on the day](#expected-load-on-the-day).
- Four behaviour problems were found. None is a capacity problem. Two of them matter before the 12th:
  1. **A photo the couple removes can come back** (deleted while still uploading, or re-sent by the phone afterwards).
  2. **No moderation queue exists**, so "reject before it shows" isn't possible today.
- No production behaviour was changed. Each fix below is a proposal.

## How it was run

Running against a *preview* of the production Worker wasn't safe: `wrangler.jsonc` has a single D1/R2 binding, so a preview version writes into the production database and bucket. With your OK I ran the test on an isolated copy instead:

| | Production (untouched) | Test stack (deleted afterwards) |
|---|---|---|
| Worker | `madeofmemories` | `madeofmemories-loadtest` (workers.dev) |
| D1 | `wedding-album` (APAC) | `wedding-album-loadtest` (APAC) |
| R2 | `wedding-album-media` (APAC) | `wedding-album-media-loadtest` (APAC) |
| Code | `src/index.js` @ ab0817b | the same file, wrapped by `loadtest/worker.js` (adds key-guarded `/__lt/` list/purge routes only) |

Same regions as production, served from the SIN colo. Test event: `load-test-2026-11-24-3z3c`, private. The app always adds a 4-character suffix, so the slug can't be exactly `load-test-<date>`.

Harness: `loadtest/harness.mjs`. It refuses to run unless the URL contains `loadtest`, and refuses the production slug. Each simulated guest behaves like `public/guest.js`:

- Joins, then sends one file at a time: thumb PUT, then media PUT.
- Polls the feed every 20 s.
- Has its own connection pool.
- Files: 2–8 MB, 70 % JPEG with a preview, 30 % HEIC sent raw without one (the client's fallback when it can't decode).
- About 5 % of uploads are aborted partway through the body. Like the client, most are then retried with the same id; about 30 % are abandoned.
- About 10 % are duplicates: half re-sent after success, half sent twice in parallel.
- The 60-guest stage added one 120 MB video (multipart, 12 × 10 MB pieces) and a photobooth: a 3 MB strip as a guest every 20 s, plus the couple's admin strip slot replaced every minute. `web/booth` has no network code, so this is an assumption about how strips arrive.

Server-side CPU and wall time come from `wrangler tail`. It samples under load, so those figures cover 4,082 of ~8,200 requests.

Caveats:
- **All traffic came from one machine.** Its uplink peaked at 66 MB/s, so client latency above 60 guests is mostly that uplink. A venue also puts every phone behind one public IP, so the single-IP test is representative for rate limiting.
- **The payloads were bigger than real uploads.** On a phone, `guest.js` re-encodes photos to ≤2000 px JPEG (~0.4–1 MB) before sending. Raw 2–8 MB files are a pessimistic case.

## Limits this design runs into (step 1)

Per-request costs, read from `src/index.js`. Cloudflare limits are for the Workers Paid plan, checked against the current docs.

| Limit | Platform value | What the upload path uses | Headroom |
|---|---|---|---|
| Subrequests per request | 10,000 | media PUT: 5 (D1 event, D1 dup check, D1 guest, R2 put, D1 insert). Thumb: 2. Feed: 2. Video piece: 4. **+8 D1 statements on the first API request in each new isolate** (`ensureSchema`) | Not a factor |
| CPU per request | 30 s default (5 min max) | measured max 27 ms, p95 ≤ 12 ms | Not a factor |
| Memory | 128 MB per isolate | bodies are streamed into R2, never buffered | Not a factor |
| Request body | 100 MB (Free/Pro zone), 200 MB (Business) | single PUT capped in code at **95 MB** (`MAX_MEDIA_BYTES`). Client switches to 10 MB pieces above **20 MB** (`LARGE_FROM`) | OK |
| D1 throughput | single-threaded per database; ~1,000 q/s at 1 ms per query | 3 reads + 1 write per photo. Peak in test: ~13 uploads/s, about 55 queries/s, no errors. The real event is ~0.2 uploads/s | ~50× at peak test load |
| D1 writes | 50 M rows/month included | 1 row per photo, 1 per guest. Event total ≈ 1,000 | Not a factor |
| R2 operations | Class A billed, no rate limit except same-key | 2 per photo (thumb + media). A 120 MB video is 14 (start + 12 pieces + complete). Event total ≈ 1,500 | Not a factor |
| R2 same-key writes | 1 per second per key (429 above) | only hit by a parallel duplicate of the same id. 155 parallel duplicate pairs in test, no 429s | Not a factor |
| R2 multipart | parts ≥ 5 MiB (uniform), ≤ 10,000 parts; unfinished uploads auto-aborted after 7 days | 10 MB pieces; code ceiling **1 GB** (`MAX_LARGE_BYTES`) | OK |

Single-file ceilings found in code:

| What | Ceiling |
|---|---|
| Single-PUT photo/video | 95 MB |
| Multipart video | 1 GB |
| Preview thumb | 1 MB |
| Cover, strip | 10 MB |
| Poster | 25 MB |
| Voice wish | 10 MB |
| Demo album | 25 MB, 12 items per visitor |

The size checks trust the `Content-Length` header.

**What hits first:** none of these. The first real constraint is the venue uplink, then the one-file-at-a-time queue on each phone.

## Failure paths (step 4)

Script: `loadtest/failures.mjs`. Output: `loadtest/results/failures.json`.

**Observed platform behaviour that explains all of the timing results:** Cloudflare receives the whole request body before the Worker runs. The rerun confirmed this 3/3 times: closes at 0.4 s, 1.6 s and 3.1 s into a 3.8 s body all returned 403. So every check (token, status, duplicate) happens **at the end of the upload**, after the guest has already spent the bandwidth.

| # | Scenario | Result | Verdict |
|---|---|---|---|
| 1a | Guest link renewed (owner reset) after a photo's body has arrived | 201, photo stored | expected |
| 1b | New upload with the old token | 401 `bad_token` | pass |
| 1c | Video: pieces 1–2 sent, link renewed, piece 3 | 401 `bad_token`. The R2 multipart upload is left unfinished; R2 auto-aborts it after 7 days | **finding (fix 3)** |
| 1d | Same guest with the new token | 201: the guest record survives a link renewal | pass |
| 2a | Event closed while a photo is uploading | 403 `closed` when the body finishes. The phone keeps the file and retries every minute | pass (bandwidth wasted, nothing lost) |
| 2b | New upload while closed | 403 `closed` | pass |
| 2c | Video piece while closed | 403 `closed` | pass |
| 2d | Reopen → resume video from piece 3 → close before complete → reopen → complete | complete 403 while closed, 201 after reopening; earlier pieces were reused | pass |
| 3a | Couple deletes an item while it is still uploading | DELETE returns `{"gone":true}`, then the upload lands and **the item is visible** | **finding (fix 1)** |
| 3b | Couple deletes an item, then the phone re-sends the same id (lost response, resumed queue) | 201 and **the item is back** | **finding (fix 1)** |
| 3c | "Moderation reject" | Doesn't exist. `schema.sql` documents privacy `approve`, but the code accepts only `public`/`private`, and nothing writes `media.approved = 0` | **finding (fix 2)** |
| 4a | Photo the phone couldn't decode/rotate (raw HEIC, no preview, no size) | 201. Thumb 404. The gallery falls back to the full original (`image/heic`, 2–8 MB per tile), which only Safari can display | **finding (fix 4)** |
| 4b | JPEG with EXIF Orientation=6, not redrawn | stored and served byte-for-byte with the tag intact | pass |

On EXIF: the Worker never decodes or rotates images. Rotation happens on the phone: `createImageBitmap` applies EXIF orientation, then the canvas redraw bakes it in. In the fallback path the viewing browser applies it from the original file. So "fails EXIF rotation" in practice means "the phone couldn't decode the file", which is 4a. I could only test the server side of that here, not `createImageBitmap` on a real iPhone. iPhones decode their own HEIC in Safari, so for this crowd 4a should mostly affect Android or desktop guests who pick HEIC files.

## Fixes: smallest change for each

None of these are deployed. Fix 1 is written on branch `fix/removed-media-stays-removed` (not yet committed or merged); the rest need your OK.

1. **A removed item comes back (3a, 3b).** *Implemented on the branch:*
   - A `removed_media` table (in `MIGRATIONS` and `schema.sql`). Both delete routes record the id there, including a couple's delete of an id that hasn't arrived yet. A guest's delete of an unknown id does not, so a guest can't block someone else's upload.
   - Uploads check the table before storing. The media insert is conditional on the id not being removed; if it was removed mid-upload, the file and preview are deleted and the reply is `200 {"removed":true}`. Single PUT and multipart both go through this path.
   - `guest.js` drops such an item from the queue without counting it as shared.
   - Owner reset (clear) and the nightly demo cleanup also clear the table.
   - Verified with `loadtest/removed.mjs` against `wrangler dev`, using local D1/R2 only: 10/10 pass, and the removed files return 404. The window where a delete lands *between* the R2 write and the insert can't be timed on purpose; that branch is covered by the conditional insert, not by a test.

   Original proposal: Most important for the 12th: a removed photo reappearing is exactly what a couple notices.
   Smallest change: on delete, keep a tombstone instead of forgetting the id. Add `CREATE TABLE IF NOT EXISTS removed_media (id TEXT PRIMARY KEY, event_id TEXT NOT NULL)` to `MIGRATIONS`. `deleteMedia`/`adminDeleteMedia` insert the id, even when no row exists yet. Then make the insert in `uploadMedia`/`completeParts` conditional:
   ```sql
   INSERT OR IGNORE INTO media (...) SELECT ... WHERE NOT EXISTS (SELECT 1 FROM removed_media WHERE id = ?)
   ```
   If the row didn't go in, delete the R2 object. About 12 lines. The same applies to wishes if wanted.
2. **No moderation queue (3c).** If the couple wants approve-before-publish, the smallest version is:
   - Add `'approve'` to `PRIVACY`.
   - Insert with `approved = (privacy === 'approve' ? 0 : 1)`.
   - Add `PUT /api/admin/:slug/media/:id/approve`.

   The feed already filters `approved = 1`. It needs a small admin UI too, so it's realistic for the 12th only if you want it. Otherwise keep delete-after (with fix 1).
3. **Renewed link mid-upload drops the phone's queue (1c).** In `guest.js`, `bad_token` does `queue = []`. That wipes the in-memory queue; IndexedDB copies survive only until the next load with a bad token. Smallest change: replace `queue = []` with `setPaused(true)` plus the toast, so files stay queued until the guest re-scans. The unfinished multipart upload needs no change (auto-aborted after 7 days). Only matters if you plan to renew the guest link during the event.
4. **Undecodable photo: blank, heavy tile (4a).** Smallest change, in `guest.js` `tile()` and in `admin.html`: when the thumb fails and `it.url` ends in `.heic`/`.heif`, show a plain "photo" tile instead of loading the original. The couple can still download it. Converting to JPEG server-side would need Cloudflare Images; not worth it for the 12th.
5. **Orphaned previews (67 objects, ~4 MB).** Harmless: not shown, and removed by owner reset. Optional fix: send the thumb after the media succeeds, or let expiry cleanup sweep `thumbs/` by prefix.
6. **`ensureSchema` on every new isolate** (not a failure, just cost). Before the first API request in each isolate it runs 8 statements against D1, including an `UPDATE`, which is a write. That adds latency to the first request a guest makes on a fresh isolate, and probably accounts for some of the join p95 (~0.5 s, not measured in isolation). Smallest fix: apply the migrations once (`npm run db:remote` / a migration file) and remove `ensureSchema` from the request path, or guard it with one `SELECT` of a schema-version setting. Low priority.

Also noted, no change needed:
- A parallel duplicate of the same id makes two R2 writes and returns 201 to both; one row results.
- README line "Workers accept up to 100 MB per request on the free plan" should say the limit depends on the **zone** plan (Free/Pro 100 MB). The code's 95 MB cap is correct for that.

## Expected load on the day

80 guests × ~8 photos in 60 minutes ≈ 640 uploads. That's ~0.2 per second, against 13 per second sustained in this test. With on-phone re-encoding that's about 0.5 GB per hour, roughly 1.1 Mbit/s of venue uplink on average. A few 100 MB+ videos add bursts. What to check at the venue is upstream bandwidth and Wi-Fi client limits, not Cloudflare.
